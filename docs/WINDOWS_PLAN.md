# Windows 实现建议

这份文档是助手提出的实现建议，尚未开始编码，技术栈和界面细节也未由用户逐项确认。用户需求和平台决定以[产品定义](PRODUCT.md)为准。

## 推荐技术方向

首个 Windows 原型建议使用 C#、.NET 10 LTS、WPF 和 Win32 系统接口。WPF 提供桌面窗口、选择列表、键盘交互和布局预览，Win32 负责枚举和调整其他应用的窗口。官方资料见[研究依据](REFERENCES.md)。

.NET 10 的当前支持政策覆盖到 2028 年 11 月 14 日。实施时采用受支持的最新补丁。WPF 仅运行于 Windows，未来 macOS 界面需要单独实现，不把 WPF 描述成跨平台方案。

先将布局计算与系统窗口操作分开，便于验证计算结果。首版用一个桌面应用承载三处职责即可：

| 职责 | 处理的内容 |
| --- | --- |
| 选窗与预览 | 前台目标捕获、多选列表、选择顺序、布局切换、应用和恢复入口。 |
| 布局计算 | 根据工作区域、窗口数量和顺序生成目标矩形，不直接调用系统接口。 |
| 系统窗口操作 | 候选窗口筛选、位置快照、身份检查、应用排布、结果读取和恢复。 |

原型只需要本地桌面能力，无需外部服务、账号或 API 密钥。

## 窗口选择范围

布局显示器以打开面板前的前台窗口为准，目标范围使用该显示器扣除任务栏后的工作区域。若原前台窗口不符合条件，回退到鼠标所在显示器，面板从空选择开始。

首版候选窗口也限定在该显示器和当前虚拟桌面。跨显示器选择属于后续产品决定，不和布局目标显示器混淆。

- 用 `EnumWindows` 枚举桌面应用的顶层窗口，它本身不能完成可选窗口筛选。
- 用 `IVirtualDesktopManager.IsWindowOnCurrentVirtualDesktop` 判断桌面归属，并通过 `DWMWA_CLOAKED` 等信息排除被系统隐藏的窗口。
- 排除 PaneSet 自己的窗口、桌面和任务栏、工具窗口、模态附属窗口，以及首版未支持的最小化、全屏和不可调整大小窗口。
- 正常窗口和最大化窗口作为支持目标，最大化状态恢复需要单独验收。
- 被其他窗口盖住、但属于当前范围的普通窗口仍列为候选。同一应用的多个窗口保持独立身份。
- 窗口标题用于显示和搜索，不能作为唯一身份。应用和恢复时重新验证句柄、进程身份及窗口特征，匹配不可靠时跳过并说明。

窗口筛选和各类应用的支持情况需要真实原型验证，不能仅依据枚举结果承诺兼容。

## 排布和恢复

布局计算统一使用明确的坐标单位。WPF 的设备无关单位与系统窗口坐标要在边界处转换，并验证缩放比例、任务栏位置、负坐标及窗口可见边框的影响。

在用户最终确认后、第一次修改窗口前，重新校验目标并获取最新的位置和 `GetWindowPlacement` 显示状态，保存为本次恢复快照。若变化使预览失效，则返回预览重新确认，不执行旧方案。

调整窗口时使用适当的 `SetWindowPos` 标志，避免为修改尺寸反复激活窗口或意外改变置顶状态。读取实际结果，区分成功、应用尺寸限制、目标消失和系统调用失败。系统接口返回成功不保证应用接受了预期的完整尺寸。

一个请求可以包含多扇窗口，但不是原子事务。某个目标失败时，保留每扇窗口的结果和本次已受影响目标的快照，用户可以恢复受影响窗口。重复应用期间只允许一个排布请求在执行，避免前后操作互相覆盖。

恢复按钮只处理最近一次请求的受影响窗口。通过身份检查的存活目标恢复原位置、大小和正常或最大化状态。窗口已经关闭、显示器变化或应用限制导致无法精确恢复时，报告部分结果，不打开新窗口或把位置写到身份不匹配的目标上。

普通权限下无法控制的窗口给出明确反馈。默认运行方式保持普通用户权限，管理员应用和受限窗口的支持需要独立验证。

## 下一步交付

下一个可运行成果应是一个真实 Windows 小程序：在选窗面板中选两扇普通窗口，展示并排预览，应用后读取实际位置，并能恢复本次调整。手动启动入口已经足以验证这条流程。

在两窗流程通过后，同一个程序增加三窗布局和快捷键入口。全局快捷键注册失败时，给出冲突提示，保留手动入口。

原型完成后按[产品定义中的任务比较](PRODUCT.md#如何判断是否值得继续)记录操作成本，再决定是否继续扩展。网页里的窗口卡片可以验证布局理解，但不能证明系统窗口控制有效。

## 验收建议

| 情况 | 通过条件 |
| --- | --- |
| 两个不同应用的窗口 | 一次确认完成并排，读取到合理的实际位置和大小。 |
| 同一应用的两三个窗口 | 能独立选择目标，不把应用等同于一扇窗口。 |
| 三窗等宽与一主两辅 | 顺序和预览对应，交换位置后结果一致。 |
| 窗口被遮挡 | 能在面板中选择，不要求先逐个激活目标。 |
| 取消预览 | 实际目标窗口没有被移动或缩放。 |
| 未选中的窗口 | 位置、大小和显示状态保持不变。 |
| 目标在确认前关闭 | 跳过失效目标并说明，不误操作其他窗口。 |
| 排布后一个目标关闭 | 恢复其余身份匹配的受影响窗口，说明关闭目标已跳过。 |
| 最小尺寸或权限阻止排布 | 展示实际结果和限制，不显示整组成功。 |
| 原窗口处于最大化状态 | 排布后能恢复原显示状态，失败时给出说明。 |
| 100%、125%、150% 缩放 | 布局与预览对齐，目标不覆盖任务栏。 |
| 其他虚拟桌面、系统隐藏或工具窗口 | 按范围排除，不误列为普通候选。 |
| 重复确认或快速再次触发 | 排布请求按明确顺序处理，恢复快照对应最近一次请求。 |

布局计算适合用小型自动测试验证两窗和三窗矩形、边界、间距、像素舍入及异常工作区域。系统窗口筛选、焦点、最大化恢复和应用限制用真实 Windows 窗口验证，记录系统版本和参与应用。测试代码在实现相应行为时添加，本轮没有应用测试可运行。

## 当前环境检查

当前主机为 Windows 10 Pro 22H2、AMD64，系统版本 19045。会话是可交互桌面，有两台显示器。本轮在当前 PATH 和四个常见安装目录未发现 `dotnet`，尚未安装 SDK 或创建应用工程。

.NET 10 的[官方系统支持列表](https://raw.githubusercontent.com/dotnet/core/main/release-notes/10.0/supported-os.md)没有列出当前的 Windows 10 Pro 22H2。前文的 LTS 支持结束日期不代表这台主机也处于官方支持范围。原型是否能够运行仍可通过实际构建和启动验证，发布产品的系统支持范围需要另行明确。

已确认 Microsoft 提供 Windows x64 SDK ZIP，发布元数据包含下载地址和 SHA-512 校验值。若采用推荐技术栈，先校验并准备局部 SDK，再运行工具链、构建 WPF 程序并启动受控窗口，记录在当前主机上的实际结果。SDK 尚未下载，工具链准备方式和流程配置见[下一步草案](SETUP_REVIEW.md)。
